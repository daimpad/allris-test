Ratsatlas Bonn Zur Karte

So funktioniert der Ratsatlas

Woher kommen die Daten des Ratsatlas, was passiert mit ihnen und wann wird die Seite neu erzeugt? Vier Grafiken zeigen es, vom Überblick bis zur Technik. Sie entstehen aus dem Code im Repository und zeigen den Aufbau, nicht den Verlauf einzelner Läufe.

Auf dieser Seite: Überblick · Datenfluss · Zeitplan · Technik · Grenzen

Überblick

Die Karte erfindet nichts: Sie holt öffentliche Daten der Stadt Bonn und weiterer Stellen, ordnet sie jeden Morgen neu und zeigt sie so, dass man sie nach Ort, Zeit und Zuständigkeit finden kann. Was die Karte selbst erschließt, etwa den Ort einer Vorlage, ist als abgeleitet gekennzeichnet.

Alle Kästen erklärt
  • Ratsinformationssystem der Stadt: Hier stehen alle Vorlagen, Sitzungen und Gremien. Die Stadt stellt sie als offene Daten bereit.
  • Spiegel mit Ergebnissen: OParl-Lite ergänzt Tagesordnungen, Ergebnisse und die Texte der Dokumente.
  • Karten und Flächen: Ortsteile, Stadtbezirke und Bebauungspläne der Stadt, Straßen aus OpenStreetMap.
  • Weitere offene Daten: Haushalt, Zensus, Haltestellen, Baustellen, Mängelmelder und Wahlbeteiligung.
  • Abholen: Ein Programm holt die Daten jeden Morgen neu ab; bei einem Ausfall bleibt der Stand des Vortags.
  • Verorten: Es sucht in Titeln und Texten nach Straßen, Ortsteilen und Bebauungsplänen und markiert, wie sicher ein Ort ist.
  • Ordnen: Es ordnet Beratungen zu einer Prozesslinie, ermittelt den Stand und ordnet Themen zu.
  • Prüfen: Es prüft Datenschutz und Kennzahlen; erst dann wird veröffentlicht.
  • Karte und Liste: Vorlagen auf der Karte und in einer Liste, mit Filtern und Zeitleiste.
  • Themen- und Gebietsseiten: Zusammenfassungen je Thema und je Ortsteil, mit Haushalt und Sitzungen.
  • Feeds und Kalender: Neues abonnieren, Sitzungen im eigenen Kalender.
  • Offene Daten: Alles zum Herunterladen und Weiterverwenden.
  • Bürger:innen: Sehen, was in der eigenen Nachbarschaft beraten wird, und mitwirken.
  • Politik und Verwaltung: Vorgänge und Zuständigkeiten schneller finden.
  • Presse und Initiativen: Verfahren verfolgen und belegen, mit Link zum Original.
  • Weiterverwendung: Apps, Forschung und andere Seiten nutzen die offenen Daten.

Datenfluss

Jeder Kasten in der Mitte ist ein Schritt der Pipeline, aufgerufen mit python -m pipeline <schritt>, in der Reihenfolge des Hauptlaufs. Links stehen die Quellen mit ihrer Lizenz, rechts die Ergebnisse. Die Liste der Schritte liest diese Seite aus dem Workflow; kommt ein Schritt hinzu, erscheint er hier.

Alle Kästen erklärt
  • Ratsinformationssystem: Die OParl-Schnittstelle der Stadt Bonn: Vorlagen, Gremien, Ämter, Sitzungen und Orte. Hauptquelle der Karte. Lizenz: CC0 1.0 (Stadt Bonn, Datensatz „Ratsinformationssystem OParl-API“). Quelle
  • OParl-Lite: Ein Spiegel des Ratsinformationssystems von machdenstaat mit Tagesordnungspunkten, Ergebnissen und Texten der Dokumente. Lizenz: CC BY 4.0 (OParl-Lite Bonn, machdenstaat). Quelle
  • OpenStreetMap: Straßen, Namen von Gebäuden und Anlagen und die Daten der grauen Karte. Lizenz: ODbL 1.0, © OpenStreetMap-Mitwirkende. Quelle
  • Ortsteile und Stadtbezirke: Flächen der 51 Ortsteile und 4 Stadtbezirke aus dem Open-Data-Portal der Stadt. Lizenz: CC0 1.0 (Stadt Bonn). Quelle
  • Bebauungspläne: Geltungsbereiche der rechtskräftigen Bebauungspläne der Stadt. Lizenz: CC0 1.0 (Stadt Bonn, Datensatz „Lage der Bebauungspläne“). Quelle
  • Hausnummern: Georeferenzierte Hausnummern der Stadt, nur zur Bestimmung des Ortsteils. Lizenz: CC0 1.0 (Stadt Bonn, Datensatz „Hausnummern georeferenziert“). Quelle
  • Haushalt: Haushaltspläne und Jahresabschluss der Stadt (PDF), einmalig ausgelesen und von Hand geprüft. Keine Lizenzangabe der Stadt. Seite
  • Zahlen zum Gebiet: Zensus 2022, Kitas, Bodenrichtwerte, Klimaanalyse, Überschwemmungsgebiete, Haltestellen und Wahlbeteiligung, je mit eigener Lizenz.
  • Baustellen und Mängelmelder: Offene Daten der Stadt Bonn (CC0), täglich im eigenen Archiv gespeichert.
  • Vorlagen: Holt die Vorlagen über die OParl-Schnittstelle der Stadt Bonn (CC0). Bricht ein Abruf ab, bleibt der Stand des letzten Laufs. Code (pipeline/fetch.py)
  • Gremien und Ämter: Holt Gremien, Ämter und Verwaltungsbereiche; daraus stammt das federführende Amt einer Vorlage. Code (pipeline/fetch.py)
  • Besetzung: Holt die laufenden Mitgliedschaften in den Gremien, als Auszug ohne Kontaktdaten. Code (pipeline/besetzung.py)
  • Sitzungen: Holt Sitzungen und Wahlperioden für Kalender, Fristen und Zeitleiste. Code (pipeline/fetch.py)
  • Bebauungspläne: Holt montags die Geltungsbereiche der rechtskräftigen Bebauungspläne der Stadt (CC0). Code (pipeline/fetch.py)
  • Hausnummern: Holt montags das Hausnummernverzeichnis der Stadt. Es dient nur dazu, den Ortsteil einer Straße zu bestimmen; Hausnummern erscheinen nicht auf der Karte. Code (pipeline/fetch.py)
  • Gebäude und Anlagen: Holt montags Namen von Gebäuden und Anlagen aus OpenStreetMap (ODbL), um Vorlagen über ihren Titel zu verorten. Code (pipeline/fetch.py)
  • Haltestellen: Holt am 1. des Monats die Haltestellen des VRS für die Zahlen je Ortsteil. Code (pipeline/kontext.py)
  • Texte der Dokumente: Holt Texte von Hauptdokumenten über OParl-Lite, höchstens 3.000 je Lauf. Sie dienen nur der Verortung und werden nicht veröffentlicht. Code (pipeline/fetch.py)
  • Beratungen: Holt Sitzungen, Tagesordnungspunkte und Ergebnisse aus OParl-Lite (CC BY 4.0); daraus entsteht die Prozesslinie einer Vorlage. Code (pipeline/fetch.py)
  • Datenbank und Verortung: Baut eine SQLite-Datenbank aus Vorlagen, Beratungen, Sitzungen, Gremien und Ämtern, verortet Vorlagen nach festen Regeln und leitet den Stand jedes Vorgangs ab. Code (pipeline/build.py)
  • Stufe C (angehalten): Verortung mit einem Sprachmodell. Sie ist nicht freigegeben und stellt derzeit keine neuen Anfragen. Code (pipeline/stufe_c.py)
  • Export: Schreibt je Gebiet eine Datei für die Karte, dazu Feeds, Kalender, GeoJSON, Prüfprotokolle und die Daten der Themenseiten. Code (pipeline/export.py)
  • Zahlen je Ortsteil: Rechnet Kennzahlen je Ortsteil aus Zensus, Bodenrichtwerten, Haltestellen, Kitas, Hitze, Überschwemmung und Wahlbeteiligung um (abgeleitet). Code (pipeline/kontext.py)
  • Prüfung: Prüft Kennzahlen und Datenschutz, etwa dass keine Hausnummern von Privatpersonen in Ortsangaben stehen. Schlägt eine Prüfung fehl, bricht der Lauf ab. Code (pipeline/check.py)
  • Verfahren nach Regelwerk: Ordnet jedem Vorgang ein Verfahren nach dem Soll-Modell zu und vergleicht es mit den tatsächlichen Beratungen. Code (pipeline/soll.py)
  • Baustellen: Bereitet das eigene Archiv der Baustellen für die Karte auf. Code (pipeline/kandidaten.py)
  • Mögliche Umsetzungen: Sucht Baustellen, die zu einem Baubeschluss passen könnten (Ort, Zeit, Straße, Amt). Die Karte zeigt nur Treffer mit hoher Übereinstimmung, als Hinweis, nicht als Beleg. Code (pipeline/kandidaten.py)
  • Mängelmelder: Zählt die Meldungen der letzten 90 Tage je Ortsteil aus dem eigenen Archiv. Code (pipeline/anliegen.py)
  • Abgleich: Vergleicht eine Stichprobe der aufbereiteten Daten mit der OParl-API der Stadt. Code (pipeline/verify.py)
  • Datenpaket: Packt Daten, Prüfprotokolle und Lizenzen in ein Zip-Paket zum Herunterladen. Code (pipeline/verify.py)
  • Statische Seiten: Schreibt Themen-, Gebiets- und Erklärseiten wie diese, dazu robots.txt und sitemap.xml. Code (pipeline/seo.py)
  • Kurzfassungen: Lässt nach dem Veröffentlichen neue Kurzfassungen mit Mistral schreiben (gekennzeichnet, mit Prüfung auf wörtliche Übernahmen). Sie erscheinen mit dem nächsten Lauf. Code (pipeline/kurzfassung.py)
  • Karte und Liste: Je Gebiet eine JSON-Datei, die die Karte im Browser lädt; die Suche über ganz Bonn hat eine eigene Datei. Öffnen
  • Statische Seiten: Themenseiten, Gebietsseiten, Haushalt, Begriffe, Einfache Sprache und diese Seite, ohne Skript lesbar. Öffnen
  • Feeds und Kalender: Atom-Feeds je Gebiet, je Vorlage und für ganz Bonn, dazu ein Sitzungskalender (ICS). Öffnen
  • Offene Daten: GeoJSON der verorteten Vorlagen, Beschreibung nach DCAT-AP und Prüfprotokolle als TSV.
  • Datenpaket: Alle Daten, Prüfprotokolle und Lizenzen als Zip-Paket. Öffnen
  • GitHub Pages: Der Spiegel der Seite unter daimpad.github.io. Öffnen
  • Hauptadresse: Der Branch deploy enthält die fertige Seite; der Server von bonn.ratsatlas.de übernimmt ihn über einen Webhook. Öffnen

Zeitplan

Die Läufe starten von selbst zu festen Zeiten (Cron-Aufträge in GitHub Actions). Die Zeiten sind in UTC angegeben; in Bonn ist es eine Stunde später, im Sommer zwei. Manche Abrufe laufen nur montags oder am Monatsersten innerhalb des Hauptlaufs.

Alle Kästen erklärt
  • Kartenkacheln: am 7. Januar, April, Juli, Oktober um 03:23 UTC (in Bonn 04:23 Uhr, im Sommer 05:23 Uhr). Auslöser: am 7. Januar, April, Juli, Oktober um 03:23 UTC, bei jedem Pull Request, auf Knopfdruck. Erzeugt vierteljährlich die grauen Kartenkacheln für Bonn aus OpenStreetMap-Daten und legt sie im Branch kacheln ab. Workflow kacheln.yml
  • Hauptlauf: täglich 04:17 UTC (in Bonn 05:17 Uhr, im Sommer 06:17 Uhr). Auslöser: täglich 04:17 UTC, bei jeder Änderung an main, auf Knopfdruck. Holt die Daten, bereitet sie auf, prüft sie und veröffentlicht die Seite: auf GitHub Pages und im Branch deploy, aus dem der Server der Hauptadresse liest. Danach schreibt er neue Kurzfassungen. Workflow pages.yml
  • Archiv: täglich 05:23 UTC (in Bonn 06:23 Uhr, im Sommer 07:23 Uhr). Auslöser: täglich 05:23 UTC, auf Knopfdruck. Speichert jeden Morgen den Stand der Baustellen und die Zahl der Meldungen im Mängelmelder im Branch archiv. So entsteht eine Zeitreihe, die die Stadt selbst nicht anbietet. Workflow baustellen.yml
  • Live-Prüfung: täglich 06:41 UTC (in Bonn 07:41 Uhr, im Sommer 08:41 Uhr). Auslöser: täglich 06:41 UTC, nach jedem Hauptlauf, auf Knopfdruck. Prüft nach jedem Hauptlauf und jeden Morgen, ob Hauptadresse und Spiegel den neuen Stand zeigen und wichtige Seiten und Feeds antworten. Workflow live.yml
  • Quellen: montags 06:41 UTC (in Bonn 07:41 Uhr, im Sommer 08:41 Uhr). Auslöser: montags 06:41 UTC, auf Knopfdruck. Versucht montags, Dateien der Stadt zur Wahl 2025 abzurufen, und legt sie im Branch quellen ab. Workflow quellen.yml
  • Kartenkacheln: am 7. Januar, April, Juli, Oktober um 03:23 UTC. Erzeugt vierteljährlich die grauen Kartenkacheln für Bonn aus OpenStreetMap-Daten und legt sie im Branch kacheln ab. Workflow kacheln.yml
  • Haltestellen (am 1.): Innerhalb des Hauptlaufs: Abruf Haltestellen (VRS; am 1. des Monats und auf Knopfdruck). Montags zusätzlich: Abruf Bebauungspläne (Geltungsbereiche, Stadt Bonn; montags und auf Knopfdruck); Abruf Hausnummern (Stadt Bonn) und Gebäude und Anlagen (OSM; montags und auf Knopfdruck). Workflow pages.yml
  • Auswertung Assistent: Auslöser: auf Knopfdruck. Stellt dem Ratsassistenten einen Katalog von Fragen und wertet die Antworten aus; nur auf Knopfdruck. Workflow eval.yml
  • Version: Auslöser: auf Knopfdruck. Erstellt eine Version mit Datenpaket; nur auf Knopfdruck. Workflow release.yml
  • Tests: Auslöser: bei jeder Änderung an main, bei jedem Pull Request. Prüft jede Änderung am Code: Python-Tests, Browser-Tests mit Playwright und Barrierefreiheit mit axe. Workflow tests.yml

Technik

Die Karte braucht keinen eigenen Rechner, der ständig läuft: Ein Python-Programm erzeugt jeden Morgen fertige Dateien, die ein einfacher Webserver ausliefert. Im Browser zeichnet Leaflet die Karte. Tests prüfen jede Änderung, bevor sie veröffentlicht wird.

Alle Kästen erklärt
  • GitHub Actions: 8 Workflows steuern Abruf, Prüfung und Veröffentlichung (Grafik „Zeitplan“). Läufe auf GitHub
  • GitHub Pages: Hostet den Spiegel der Seite. Spiegel
  • Webhosting (Plesk): Der Server der Hauptadresse übernimmt den Branch deploy über einen Webhook; .htaccess setzt Sicherheitskopfzeilen. Hauptadresse
  • Branches: Neben main: archiv, auswertung, deploy, else, fi, git, kacheln, kurzfassungen, quellen. Sie halten die fertige Seite, Archive, Kurzfassungen, Quelldateien, Kacheln und Auswertungen getrennt vom Code. Branches
  • HTML und CSS: Statische Seiten ohne Server-Programm; Glas-Stil, WCAG 2.1 AA.
  • JavaScript: Eigener Code ohne Framework für Karte, Liste, Zeitleiste und Tour. Code (site/app.js)
  • Leaflet 1.9.4: Bibliothek für die Karte, mit Markercluster; lokal eingebunden, ohne fremde Server. Leaflet
  • Graue Kacheln: Kartenhintergrund vom eigenen Server, erzeugt aus OpenStreetMap-Daten; „Farbige Karte“ lädt Kacheln von OpenStreetMap. Code
  • Ratsassistent: Fragen gehen direkt aus dem Browser an den gewählten Anbieter, mit eigenem Schlüssel; die Seite speichert keine Fragen. Code
  • unittest: 35 Dateien mit Python-Tests für Pipeline und Seiten. Tests
  • Playwright 1.56.1: 4 Dateien mit Browser-Tests bei 1440 und 390 px. Tests
  • axe-core 4.10.2: Prüft die Barrierefreiheit (WCAG 2 A und AA) in den Browser-Tests. axe-core
  • Python 3.12: Die Pipeline in python -m pipeline, ein Schritt je Aufgabe (Grafik „Datenfluss“). Code
  • SQLite: Datenbank eines Laufs; sie wird nicht veröffentlicht, nur ihre Exporte. Code
  • shapely: Python-Paket aus requirements.txt: Geometrie, etwa ob ein Punkt in einem Ortsteil liegt PyPI
  • pyproj: Python-Paket aus requirements.txt: Umrechnung zwischen Koordinatensystemen PyPI
  • pyshp: Python-Paket aus requirements.txt: Lesen von Shapefiles, etwa der Kontextdaten PyPI
  • cairosvg: Python-Paket aus requirements.txt: Bild der Themenseite als PNG zum Teilen PyPI
  • OParl (JSON): Offener Standard für Ratsinformationssysteme; die Stadt Bonn bietet ihn an. OParl
  • GraphQL: Abfragesprache von OParl-Lite für Beratungen und Texte.
  • GeoJSON: Flächen der Stadt und die verorteten Vorlagen.
  • PDF: Haushaltspläne und Jahresabschluss, einmalig ausgelesen.
  • Overpass: Abfragen an OpenStreetMap für Straßen, Gebäude und Anlagen.

Grenzen

  • Diese Seite zeigt den Aufbau. Ob ein Lauf gelungen ist, zeigt GitHub: Läufe der Workflows.
  • Einmalige Schritte, etwa das Auslesen der Haushaltspläne oder die Prüfbögen der Themenseiten, laufen nicht automatisch und fehlen im Zeitplan.
  • Der Server der Hauptadresse übernimmt den Branch deploy von sich aus; sein Zeitpunkt steht nicht im Repository.
